# Shopee 官方仓全流程智能补货系统

面向 **Shopee 跨境官方仓（FBS/海外仓）** 卖家的补货测算、申报与装箱自动化工具，支持 MY / TH / PH 三站点差异化规则。

v2.1.0 起同时提供 **两种运行方式**：本地 Python 后端（保真最高）与纯浏览器单文件（零依赖）。

## 一、本次修复了什么（v2.1.0）

### 2. 顺带修复的 5 个数据准确性问题

1. **TH / PH 阶段一误用马来模板**：`resolve_sheet` 用 `'th' in 表名` 匹配中文表名「泰国补货模板」必然失败，回落到第一个工作表（马来），导致菲律宾按 17 列模板写入而实际应为 16 列，备注/货值列错位。→ 改为中文别名优先匹配。
2. **阶段一覆盖模板公式**：原代码用 `=E+F`、`=2*D` 等简化公式覆盖模板自带的 `IF(ISBLANK(...))` 空值保护公式，空白行会显示 0。→ 改为只写入 4 个变动源（D/E/F/M）与测算结果（K），公式全部保留。
3. **`箱子 #1` 表头误匹配 `箱子 #19`**：字符串包含判断导致箱号列起点错位（实测写到了箱子 #19 的位置）。→ 新增精确匹配 `is_box_header()`。
4. **阶段四三重校验是假实现**：`validate_system()` 直接返回「451/451 通过」「100% 闭环」等写死结果。→ 改为真实执行 SKU 字典对齐、装箱闭环平衡、单箱尺寸重量三项校验，并给出具体差异明细。
5. **桌面版默认值指向模板文件**：`gui.py` 里「马帮销量表」「库存表」的默认值被设成补货模板文件，直接点是会拿模板当数据源。→ 改为空。

## 二、两种运行方式

### 方式 A：本地后端引擎（推荐，保真最高）

```
双击 run_web.bat
```

- 自动检查 `python` 与 `openpyxl`，启动本地服务并打开浏览器（默认 `http://127.0.0.1:8765`，被占用则顺延）。
- **复用 `core.py`**，与桌面版同一套算法，不存在两份实现漂移的风险。
- 生成的 xlsx 由 openpyxl 写出，**公式与条件格式（红绿预警）100% 保留**。
- 关闭命令行窗口即停止服务。

### 方式 B：纯浏览器单文件（零依赖）

```
双击 index.html
```

- 用同目录 `xlsx.full.min.js`（或 CDN）在浏览器里解析、计算、下载，无需 Python。
- **限制**：SheetJS 免费版无法写出条件格式，生成的 Excel 会丢失红绿预警填充色，公式保留。

### 自动探测

页面启动时先探测后端（同源 → `127.0.0.1:8765..8775`），探测成功走方式 A，否则自动降级为方式 B，右上角徽标会显示当前引擎。两种模式共用同一套 UI 与同一套算法。

## 三、四个阶段的真实行为

**阶段一 · 补货总表**
- 按 `SKU` 对齐马帮 30 天销量，按 `仓库SKU ID` 对齐在仓/在途与 RPA 销售速度。
- 站点上限：MY / TH 为 75 天销量，PH 为 60 天销量（PH 模板无 75 天列）。
- 需补量：`round(充足补货量 / 箱规) × 箱规`；超出上限则退一箱，仍超则退到 `min(round(充足补货), floor(上限))`；命中拦截词、无箱规、无需补货一律留空。
- 每一行都带**状态与测算说明**（已测算 / 备注拦截 / 缺箱规 / 无需补货），预览可直接复核。

**阶段二 · 入库申请表**：按 `Warehouse SKU ID` 映射【采购批准】→【* 申请入库数量】、【出口货值】→【* 单件出口申报货值】；未批准严格留空。

**阶段三 · 打包装箱**：解析 `3-7` 连箱均分与同序号多行拼箱；单品箱自动反查长/宽/高/重，混装箱留空待人工复核。

**阶段四 · 三重防呆校验**：SKU 字典对齐（列出缺失 SKU）、装箱闭环平衡（∑各箱 = 批准/总打包数量）、单箱尺寸重量（>30kg 或单边 >100cm 预警）。

## 四、箱规库与后续更新入口

箱规表（`补货箱规表.xlsx`）是需补量测算的必要输入。当前已内置：**482 个 SKU，其中 207 个维护了整箱数量**（未维护的 SKU 按规则留空）。

三种更新方式：

1. **页面按钮**：右上「🔄 上传/替换箱规表」——
   - 后端模式：持久化到 `_runtime/boxspec/`，重启后仍生效；
   - 浏览器模式：仅本次会话生效。
2. **重新内嵌（推荐，长期方案）**：
   ```bash
   python build_boxspec.py --spec "D:\桌面文件\虾皮补货文件\补货箱规表.xlsx"
   ```
   会把箱规写进 `index.html` 的 `EMBEDDED_BOXSPEC` 数据块，并记录版本号（文件 SHA1 前 8 位）、条数、生成时间、来源文件名；同时复制一份到项目根目录供后端读取。之后刷新页面即生效，**不需要改任何代码**。
3. **直接替换**：把新 `补货箱规表.xlsx` 放到项目根目录，重启 `run_web.bat`。

页面顶部状态栏始终显示 `已载入 N 个 SKU 箱规 ｜ 来源 ｜ 版本 ｜ 更新时间`，可据此确认当前生效的是哪一份。

## 五、算法口径（改动前请先确认业务）

| 列 | 公式 |
|---|---|
| 合计 G | `=IF(AND(ISBLANK(E),ISBLANK(F)),"",E+F)` |
| 补货至60天销售量 H | `=IF(OR(ISBLANK(D),D=""),"",2*D)` |
| 剩余可售天数 I | `=IF(OR(ISBLANK(D),D=0,D=""),"",E/(D/30))`（**只算在仓**，不含在途） |
| 充足补货量 J | `=IF(AND(ISBLANK(D),ISBLANK(E),ISBLANK(F)),"",H-F-E)` |
| 60天 N | `=IF(OR(ISBLANK(M),M=""),"",60*M-G)` |
| 75天 O | `=IF(OR(ISBLANK(M),M=""),"",75*M-G)` |

- 需补量基数用「2×马帮30天销量」，上限用「75×RPA销售速度 − 合计」，两者口径不同——这是模板既有设计（H 列与 N/O 列本就如此），未擅自改动。
- 模板新增的「数量」列（MY/TH 第 17 列、PH 第 16 列）由阶段一自动回填该 SKU 的整箱数量，仅作核对参考，**不参与测算**；同时该列使「出口货值」顺延至第 18/17 列，阶段二已改为按表头名取列，不受列位变化影响。
- 拦截词：`停 / 不补 / 超100cm / 超100 / 超长 / 下架 / 停产 / 无库存 / 无货 / dw不补`。
- 箱数取整使用 Python `round()` 的银行家舍入；JS 端已等价实现（`pyRound`），避免 `.5` 场景两端差一箱。

## 七、一致性测试

```bash
python tests/compare_engines.py
```

用同一套合成数据分别跑 Python 引擎与 `index.html` 内的 JS 引擎，比对：
- 三个站点的阶段一预览全部字段 + 生成的 Excel 逐单元格；
- 阶段二（填报条数、预览、Excel 逐单元格）；
- 阶段三（装箱组数、最大箱号、预览、Excel 逐单元格）；
- 三重校验的通过状态与提示文案。

当前结果：**全部一致**。任何一端改了算法，跑一次即可发现分歧。

## 八、已知限制 / 待确认事项

1. **浏览器模式不写条件格式**（SheetJS 免费版限制）。需要红绿预警请用 `run_web.bat`。
2. **拼箱/混箱的尺寸重量留空**是既有业务规则（等人工复核），不是 bug。
3. **阶段三按列位假设**：打包模板「已打包数量」表假定第 1 列为商品名称、第 4 列为仓库SKU ID、第 5 列为外部SKU ID；「总打包数」与「箱子 #1」列已改为按表头探测。若你的真实模板列位不同，需按实际表头再校一次。
4. **箱规覆盖度**：箱规表 482 个 SKU 中仅 207 个维护了整箱数量，其余（鱼线混箱、部分新品）需补量会按规则留空。按站点实际可测算覆盖：MY 135/201、TH 137/195、PH 74/90。要提升覆盖，在箱规表补「数量」列后重跑 `build_boxspec.py`。
5. **模板 SKU 与箱规表未完全对齐**：`ZERO-VX 左手 / ZERO-VX 右手` 等不在箱规表中，会显示为「缺箱规」。
